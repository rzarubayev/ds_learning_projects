Популярному стриминговому сервису Яндекс Музыка с большим каталогом — более 70 млн треков, 
чтобы облегчить пользовательский опыт необходимо создать систему персональных рекомендаций

### Склонируйте репозиторий

Склонируйте репозиторий проекта:

```sh
git clone https://github.com/yandex-praktikum/mle-project-sprint-4-v001.git
```

Создайте новое виртуальное окружение командой:

```sh
pip install -r requirements.txt
```

### Структура сервиса рекомендаций

Микросервис рекомендаций представлен в виде единой модульной структуры следующего вида:

```
    
    | 
    ├── modules\                # Директория с модулями микросервиса
    |   |
    |   ├── __init__.py
    |   |
    |   ├── recs\               # Модуль с основным сервисом рекомендаций
    |   |   ├── __init__.py
    |   |   ├── router.py       # FastAPI роутер для сервиса (/recs)
    |   |   └── service.py      # Сервисы получения рекомендаций
    |   |
    |   └── events_store\       # Модуль с сервисом хранилища событий
    |       ├── __init__.py
    |       ├── router.py       # FastAPI роутер для сервиса (/events_store)
    |       └── service.py      # Роутер FastAPI с описанием эндпоинтов и вызова обработчика
    |
    ├── config.py               # Настройки микросервиса
    └── main.py                 # Главный модуль с приложением FastAPI
```

Такая структура позволяет с минимальными усилиями разделить 
сервис рекомендаций и хранилище событий на два различных 
микросервиса. Все настройки хранятся в `.env` файле и загружаются 
посредством `pydantic_settings` в файле `config.py`.

Сервис рекомендаций имеет следующие эндпоинты:
1. GET: `/recs/{user_id}` - выдает смешанные k рекомендации
2. GET: `/recs/offline/{user_id}` - выдает только k оффлайн рекомендации
3. GET: `/recs/online/{user_id}` - выдает только k онлайн рекомендации
    
    По умолчанию `k=10`

Хранилище событий имеет следующие эндпоинты:
1. POST: `/events_store/put` - добавляет событие в хранилище, параметры: `user_id`, `item_id`
2. POST: `/events_store/get` - возвращает события пользователей, параметры: `user_id`, `k` 
(необязательное).

### Стратегия смешивания рекомендаций

Сервис рекомендаций производит смешивание рекомендаций в следующем порядке:
1. Сервис рекомендаций получает все последние события пользователя, при старте используются 5 
последних событий для всех пользователей, которые были в тренировочной выборке.
2. Сервис рекомендаций получает `k` рекомендаций (по умолчанию 10, но можно изменить в 
процессе тестирования) за исключением ранее прослушанных треков, для горячего пользователя 
- персональные рекомендации, в противном случае самые популярные. Таким образом, при отсутствии 
онлайн рекомендаций новый пользователь получит `k` оффлайн рекомендаций.
3. Сервис рекомендаций получает `k * ONLINE_RATIO` (по умолчанию соотношение 0.5, т.е. 5 
соответственно) онлайн рекомендаций исходя из значений списка `LAST_TRACK_RATIO` 
(по умолчанию [0.5, 0.3, 0.2]) в следующем порядке:
    - Если количество значений в `LAST_TRACK_RATIO` больше или равно количеству прослушанных 
    треков, то получает `LAST_TRACK_RATIO` рекомендаций - 2, 2, 1 по последним прослушанным 
    трекам при `10 * 0.5`;
    - Если количество значений в `LAST_TRACK_RATIO` меньше количества прослушанных треков, то 
    получает рекомендации по количеству прослушанных треков, в том же соотношении, но чтобы 
    их сумма была равна единице, для 1-го трека - 5 рекомендаций, для 2-х - 3 и 2 рекомендации.
4. Сервис рекомендаций смешивает по одной оффлайн и одной онлайн рекомендации поочередно, 
исключает дубликаты и возвращает `k` первых рекомендаций.

## Инструкции для тестирования сервиса

Код для тестирования сервиса находится в файле 
[test_service.py](test_service.py).

Для запуска скрипта для тестирования сервиса необходимо при запущенном сервисе рекомендаций 
в другом терминале выполнить следующую команду:

```sh
python3 test_service.py
```

Сервис позволят выполнить следующие действия:
1. Изменить адреса url сервиса рекомендаций и хранилища событий, а также количество 
рекомендаций для запроса от сервиса;
2. Получить рекомендации для одного `горячего` пользователя;
3. Получить рекомендации для одного `теплого` пользователя (было менее 5 треков в тренировочном 
датасете, либо треки появились в тестовом);
4. Получить рекомендации для нового пользователя, по которому еще не добавлялись треки;
5. Получить несколько (вводится количество) рекомендаций от пользователей без разделения 
на горячих/теплых/новых в несколько потоков по количеству ядер процессора;
6. Завершить работу сервиса.

При получении рекомендации для нового пользователя все его события помечаются как события 
`теплого` пользователя. Также все ранее направленные события помечаются как тестированные 
и не используются для рекомендаций в дальнейшем при выборе очередного пункта меню до 
перезапуска скрипта.

В файле [test_service.log](test_service.log) вывод результатов тестирования:
1. Получение рекомендаций для одного `горячего` пользователя, пункт меню - `2`;
2. Получение рекомендаций для одного `теплого` пользователя, пункт меню - `3`;
3. Получение рекомендаций для одного нового пользователя, пункт меню - `4`;
4. Получение 100 рекомендаций для всех пользователей, пункт меню - `5`;
5. Завершение работы скрипта, пункт меню - `6`.
